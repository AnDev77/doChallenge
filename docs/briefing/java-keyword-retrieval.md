# Java 공시 검색 기준선: 근거 후보만 반환

상태: 2026-11-18 구현 브랜치. 기반: SEC 수집 초안 PR #28. 공개 API와 LLM 출력은 아직 변경하지 않는다.

## 목적과 호출 순서

1. `SecIngestionRunner`의 명시적 `run-once=true` 경로에서 SEC 원문·청크의 DB 저장이 완료되면 `KeywordReadinessService.markPendingReady`를 호출한다. 기본 서버 시작이나 GET 요청에서는 실행되지 않는다.
2. 각 `PENDING` 문서의 청크가 1~1,000개인지, 순서가 0부터 연속인지, 내용·길이·SHA-256이 일치하는지 확인한다. 같은 DB 트랜잭션에서 `KEYWORD_READY`로 바꾼다. 실패하면 이번 배치의 변경은 롤백하고 원본 문서와 청크는 유지한다. 이전에 적재한 `PENDING` 문서도 다음 수집 실행에서 처리한다.
3. 후속 생성 서비스는 `EvidenceRetriever.search(symbol, query, asOf, lookbackDays, topK)`를 호출한다. 이는 **내부 Java 서비스**이며 사용자용 검색 API가 아니다. 종목과 SEC 접수 시각, 실제 적재 시각을 모두 확인한다. 같은 accession·파일명의 최신 원문 버전이 아직 `PENDING`이면 이전 버전도 숨긴다.
4. 검색어의 최대 8개 단어를 추출하고 `rag_chunk.section_text`에 부분 일치하는 후보를 최근 접수 순서로 최대 512개 읽는다. 일치 단어 수→접수 시각→문서 ID→청크 순서로 정렬해 최대 8개를 반환한다. 각 근거에는 청크·문서 ID, 원문·청크 해시, 원문 URL, accession, 접수·적재 시각이 붙는다.

여기의 `KEYWORD_READY`는 **DB 청크를 키워드 검색 가능하게 검사했다**는 표시다. 임베딩이나 Qdrant 벡터 색인을 생성했다는 뜻이 아니다. 문서 전체를 모형으로 보내거나 근거 문장을 검증하지 않는다.

## 설계 선택과 제한

- 최초 기준선은 기존 MySQL 청크를 이용한다. 새 서버·키·유료 모델 없이 출처와 시점 격리를 시험하고, 같은 평가 집합으로 임베딩 검색과 비교한 뒤 인덱스를 선택한다.
- `fetched_at <= asOf` 조건이 중요하다. 11월 17일에 접수됐어도 18일에 수집한 자료를 17일 당시 알았다고 가정하지 않는다. 공시 시각의 진실성과 과거 이용 가능 시각은 다르다.
- 정정된 원문을 읽었지만 청크 확인 전에는 과거 원문을 새 공시인 것처럼 인용하지 않는다. 다만 그 사이 해당 accession의 검색 결과는 비게 된다.
- `LIKE` 부분 일치는 동의어·의미 검색·한국어 질문과 영문 원문 사이 표현 차이를 해결하지 않는다. 후보 512개를 최근 순으로 먼저 자르므로 오래됐지만 관련성이 높은 근거가 밀릴 수 있다. 이는 측정할 기준선이며 규모 확대를 위한 최종 검색 인덱스가 아니다.
- 검색 시각은 `Instant`로 받고 DB에는 UTC로 비교한다. 비정상 입력·와일드카드/SQL 문자열은 검색어 길이 및 안전한 단어 추출·매개변수 바인딩으로 제한한다. 새 문서의 원문 파일이 실제로 영속 저장돼 있는지 다시 읽어 확인하는 과정은 아직 없다.
- 실제 SEC→MySQL 수집, 실 MySQL 검색 지연, 30건 평가 세트, 임베딩 비교, LLM 공급자 호출과 출처 의미 검증, 사람 검토·공개 조회, Kafka는 후속 작업이다. 현재 GET은 Python 내부 조회 경로다.

## 재현 경로

`EvidenceRetrieverTest`는 V3 스키마를 H2 MySQL 모드에 적용하고 같은 accession의 수정 버전, 다른 종목, 미래 접수·적재, 청크 해시 손상, 검색 순위와 출처 ID를 확인한다. 로컬 Gradle 다운로드는 실행 환경의 네트워크 제한으로 실패했으므로 테스트 통과는 아직 주장하지 않는다. Java 21 전체 시험·JAR 및 PR 게이트는 이 브랜치의 통합 단계에 확인한다.
