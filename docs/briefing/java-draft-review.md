# Java 근거 고정·초안 검토: 실행 흐름과 경계

기준일: 2026-11-18. 대상: `feat/java-briefing-publication`. 이번 작업은 **내부 초안 저장과 정확한 버전의 승인**이다. 공개 API는 아직 Python `BriefingGateway`를 사용하며 LLM, Kafka, 임베딩, 검토 UI는 미구현이다. 초안의 문장과 근거가 의미상 일치한다는 검증도 아직 없다.

## 코드가 실행되는 순서

1. 향후 생성기가 `BriefingDraftService.create(symbol, query, asOf, summary, citedChunkIds)`를 호출한다. 지금은 생성기나 내부 명령 엔드포인트가 없어 실제 운영 호출자는 없다.
2. 서비스는 `EvidenceRetriever.search(symbol, query, asOf, 7, 8)`를 호출한다. 검색은 `KEYWORD_READY`, SEC 접수/수집 시각, 같은 accession·파일명의 최신 원문 버전 조건을 적용한다. 인용 ID는 **이번 검색에서 반환된 최대 8개**에 속해야 한다. DB에 존재하는 임의의 `rag_chunk.id`만 건네서는 통과하지 못한다.
3. `asOf`는 MySQL `DATETIME(6)`에 맞춰 마이크로초로 잘라 검색과 저장에 같은 값을 사용한다. 인용 후보를 청크 ID 순으로 정렬하고, 종목·기준 시각·요약문·각 청크의 DB ID·문서 ID·원문/청크 해시·원문 URL·SEC 접수/수집 시각을 길이 접두사와 함께 SHA-256에 넣는다. **이 해시는 승인 대상 버전의 식별자이지, 내용의 사실성 보증이나 암호학적 서명이 아니다.**
4. V4의 `briefing_draft`에는 `DRAFT` 상태와 요약·해시를, `briefing_draft_evidence`에는 인용한 청크의 출처 스냅샷을 같은 DB 트랜잭션으로 저장한다. 근거 행은 `rag_chunk` FK로 원래 청크와 연결된다. 저장 중 실패하면 이 트랜잭션의 초안과 인용 행은 함께 롤백된다. 기존 SEC 원문이나 청크 저장까지 되돌리지는 않는다.
5. 검토자가 **신뢰된 내부 호출 경로에서** `approve(id, expectedSha256, reviewer)`를 실행하면 서비스는 DB에서 요약과 인용을 다시 읽고 해시를 재계산한다. 검토자가 본 해시, 저장 해시, 재계산 해시가 같을 때만 `WHERE status='DRAFT' AND content_sha256=?` 조건부 UPDATE로 승인한다. 두 요청이 같은 초안을 동시에 승인하면 한 건만 성공한다. `latestApproved(symbol)`은 승인된 행만 읽고 해시를 다시 대조한다.

## 왜 JPA 대신 JDBC인가

이 저장소에는 JPA 의존성이 있다. 이번 RAG 경로는 앞서 만든 `EvidenceRetriever`와 같은 `JdbcTemplate`/명시적 SQL을 사용한다. 문서·청크 ID와 버전·인용 스냅샷의 관계, 승인 조건부 UPDATE를 SQL에서 바로 볼 수 있게 한 선택이다. Flyway는 V4 DDL의 이력을 관리하고 DataSource/MySQL 드라이버가 DB 연결을 담당한다. `@Transactional`은 서비스 빈을 Spring 프록시로 호출할 때 초안과 근거 INSERT, 또는 승인 UPDATE를 하나의 DB 트랜잭션에 묶는다. 메서드를 직접 `new`로 만들거나 같은 객체 내부에서 자체 호출하면 그 프록시 보장을 얻지 못한다.

## 중복·실패·공개 경계

| 경우 | 결과 |
|---|---|
| 검색에서 빠진 종목·시간·`PENDING`·구버전 근거 인용 | 입력 거부, 초안 0건 |
| 같은 인용 ID를 두 번 제출하거나 인용이 없음 | 입력 거부 |
| 저장 후 요약/출처가 변경됨 | 승인 시 재계산한 해시가 달라져 거부 |
| 같은 해시로 재승인 | `DRAFT`가 아니므로 거부 |
| 미승인 초안 | `latestApproved`에 포함되지 않음 |
| 승인 후 저장된 출처 필드 변조 | `latestApproved`가 예외를 반환하여 잘못된 결과를 조회하지 않음 |

승인자는 아직 인증된 사용자 세션에서 파생되지 않고 서비스 인자다. 그래서 공개 컨트롤러나 내부 관리 API를 추가하지 않았다. 후속 작업에서는 검토자 인증·권한, 승인 감사, 승인/반려 UI, 구조화된 브리핑 계약과 의미 검증을 연결해야 한다. `APPROVED`는 이 내부 저장 구조의 승인 상태이며 현재 `GET /api/v1/briefings/{symbol}`에 노출되는 `ready`가 아니다. 결과를 생성할 LLM 공급자·모델·키/비용 한도가 없으므로 실제 LLM 호출도 아직 없다.

## 검증과 남은 조건

H2 MySQL 모드에 V3→V4를 적용하는 시험에서 `PENDING` 인용 차단, 검색 외 ID·중복 인용 거부, 마이크로초 시각과 출처 해시 보존, 검토 전 조회 차단, 잘못된/재사용된 승인 해시, 승인 후 출처 변조 시 조회 거부를 검사한다. 로컬 Gradle 8.5 배포 파일 다운로드가 네트워크 제한으로 실패했으므로 테스트 통과는 원격 Java 21 CI에서 확인해야 한다. 실 MySQL V4 마이그레이션과 실제 브리핑 생성·검토·공개 종단, 인용 문장 의미 평가, 30건 검색 평가, 임베딩, Kafka, 실제 유료 LLM은 아직 검증하지 않았다.
