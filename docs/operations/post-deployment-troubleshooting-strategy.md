## 2. 현재 상태와 역할 경계

작성 시 원격 Java main은 `0b9e926`이다. #10~#17은 열린 초안이고 #17의 head는 `a2a1306c29d469064bc8aa7fa3aa5f0741a342b1`이다. 로컬 기존 작업 트리를 보존하고 main에서 문서 전용 브랜치를 분리했다. 다음 작업자는 원격 커밋과 PR 상태를 다시 확인한다.

- Java: 회원·이메일 인증·JWT·채팅 원본·관심 목록. Python: 연구와 승인된 분석. React: 화면과 API 연결.
- 현재 React 채팅은 5초 간격 REST 조회를 사용한다. Java STOMP SimpleBroker는 앱 프로세스별이며 두 색상 간 방송 공유가 구현됐다고 가정하지 않는다.
- 메시지 원본은 MySQL. Redis는 인증 코드·증표·제한 및 기존 운동 모임 캐시를 담당한다. 금융방의 캐시는 별도 개선 대상이다.
- Flyway V1/V2, Blue/Green, IP TLS 갱신은 초안 계열에 존재한다. main에 해당 파일이 없으면 파일 누락 장애로 오해하지 말고 배포 커밋부터 확인한다.
- 격리 CI 성공, 운영 배포, 미래 예측 성능, 제품 수요를 각각 보고한다. 이 문서는 연구 성과를 입증하지 않으며 독립 미래 정답과 분석 근거가 없는 성능 주장은 HOLD다.

## 3. 배포 후 진행 순서와 완료 증거

배포가 확인된 시점을 D0로 잡는다. 아래는 작업 순서이며 하루에 반드시 끝난다는 약속이 아니다. 한 단계의 실패를 다음 단계의 성공으로 덮지 않는다.

| 단계 | 작업 | 완료 증거·중단 기준 |
|---|---|---|
| D0 실제 배포 인수 | 승인된 main/CI·이미지 SHA, 외부 IP HTTPS, 실메일 수신→인증→가입→로그인, QQQ/SPY 두 브라우저 | 타임스탬프·커밋·성공/실패를 기록. 인증서·메일·데이터 보존 중 하나라도 미확인이면 제한된 시연까지만 |
| D1 기준 측정 | 합성 데이터로 조회·쓰기·재시도·재접속 측정; 지연과 자원 사용 연결 | 데이터 크기/부하/환경/시행 수를 고정한 원본 측정 파일과 요약 |
| D2 전환·복구 | 별도 Compose 프로젝트/볼륨에서 구·신 버전, 대기 검사, 실패 전환, DB 재조회 | 동일 메시지 ID·회원·관심 목록 보존 및 실제 복귀 시간 |
| D3 병목 한 건 개선 | 느린 조회라면 실행 계획/인덱스, 반복 조회라면 캐시; 동시에 여러 변경 금지 | 변경 전후 같은 조건 3회 이상, 지연/오류/DB 부하/정확성 비교 |
| D4 사례 정리 | 원인·대안·구조 변화·회귀 시험·미해결 위험 기록 | 최대 3개 심화 사례. 개선이 없으면 미채택 이유도 결과로 기록 |

운영 서버에서 고부하·DB/Redis 중지·스키마 파괴를 실행하지 않는다. 장애 주입은 별도 볼륨을 쓰는 격리 환경에서 먼저 수행한다. 같은 EC2에서 격리 컨테이너를 띄워도 CPU·디스크는 공유되므로 운영 중 부하 시험 장소로 자동 승인하지 않는다. 실제 운영 전환은 사용자가 승인한 배포 범위와 창구에서만 진행한다.

## 4. 관측과 성능 측정 설계

### 먼저 준비할 관측 (계획, 계측 완료 아님)

- 요청별 임의 request ID를 Nginx→Java로 전달한다. 외부 입력 ID는 길이/문자를 제한하거나 새로 발급한다. 사용자 ID·JWT를 추적 ID로 쓰지 않는다.
- 구조화 로그는 시간, 서비스 버전/색상, API 경로 템플릿, 상태 코드, 처리 시간, 안전한 오류 코드, request ID 중심으로 구성한다. 요청/응답 본문·이메일·인증 코드·JWT·SMTP 설정·실제 채팅 본문은 기본 제외한다.
- 요청 ID는 로그 검색용이며 메트릭 라벨로 넣지 않는다. 메트릭 라벨은 API 템플릿·색상·결과 등 제한된 집합을 사용한다.
- Nginx 전체 요청 시간과 upstream 시간, Java p50/p95/p99·5xx·GC·스레드·DB 연결 대기, MySQL 조회/잠금 대기, Redis 지연/메모리, 컨테이너 RSS/OOM/재시작, 호스트 디스크 여유를 함께 본다.
- 프로파일러와 heap dump는 재현 환경에서 먼저 사용한다. dump에는 비밀/사용자 내용이 포함될 수 있으므로 공개 PR/에이전트 입력으로 올리지 않는다.

### 반복 가능한 부하 실험

1. 계정과 메시지는 합성 자료만 사용. 실제 SMTP는 별도 소수의 지정 수신함 시험으로 분리한다.
2. 예비 단계는 동시 사용자 1→10→30, 여유 확인 시 100. 이는 지원 인원 주장이 아니다. 단계별 1분 준비 후 5분 측정, 같은 조건 3회 이상을 초기 실험안으로 사용한다.
3. 최근 30개 조회와 `afterId` 누락 복구, 글 작성·중복 요청을 분리한다. 두 종목으로 나눈 부하와 QQQ에 몰린 부하를 비교한다.
4. REST 폴링은 사용자 N명/5초라면 대략 N/5 요청/초부터 시작한다. 설정 사용자 수와 실제 요청률·성공률을 함께 기록하고 테스트 도구가 목표 부하를 생성했는지 확인한다.
5. 합성 메시지 1만/10만 건 등 크기를 고정하고 캐시가 빈 상태와 채워진 상태를 구분한다. 부하 발생기는 가능하면 서버와 분리하고 EC2 사양·두 Java RSS·JVM 설정·커밋·도구 버전을 남긴다.
6. OOM, 데이터 정확성 실패, 급격한 디스크 부족 또는 지속적 5xx 증가 시 부하 증가를 중단한다. 실패 시점의 최대 부하를 정상 처리량으로 보고하지 않는다.

### 초기 제안 기준 — 운영 관측 뒤 재조정

| 항목 | 초기 목표 | 측정·해석 |
|---|---|---|
| 최근 조회 | p95 500ms 이하 | 합성 부하 30명, 서버 처리 시간과 외부 왕복 시간을 구분 |
| 메시지 저장 API | p95 1초 이하 | 메일 호출 제외, DB 커밋 성공과 응답 성공을 구분 |
| 다른 브라우저에 표시 | 저장 후 7초 이내 | 현재 5초 폴링 기준의 관측 목표; STOMP 지연과 별도 |
| 오류 | 해당 부하에서 5xx 1% 미만 | 의도적으로 발생시킨 401/409/429는 별도 집계 |
| 정합성 | 합성 기대 ID 기준 유실·중복 0건 | 시험 범위 내 결과일 뿐 모든 장애에서 무손실 보장 아님 |
| 앱 전환 복귀 | 실패 판정 후 2분 이내 목표 | 탐지·명령·실제 API 복구 시간을 따로 측정; 아직 실적 없음 |

p95는 요청의 95%가 그 시간 이내에 끝났다는 뜻이다. 평균만 개선되고 p99·오류가 나빠지면 채택하지 않는다. 요청 수가 적으면 p99는 불안정하므로 표본 수도 표시한다. 캐시는 같은 조건에서 DB 조회 수 또는 지연이 반복적으로 감소하고 정합성이 유지될 때 채택한다. 개선율은 `(변경 전 - 변경 후) / 변경 전 × 100`으로 계산하고 각 시행 값·중앙값·범위를 함께 남긴다. 3회 반복을 통계적 유의성 입증으로 표현하지 않는다.

## 5. 장애 시나리오와 대응 순서

| 증상/시험 | 확인·재현 | 복구·채택 조건 |
|---|---|---|
| 인증서 발급 연결 timeout | 현재 공인 IP→해당 인스턴스의 보안 그룹 80→UFW→서브넷 경로/ACL 순으로 확인 | 외부 HTTP 도달을 확인한 뒤 재발급. Nginx 설정 변경만으로 해결됐다고 추측하지 않음 |
| 인증서 만료/갱신 누락 | 만료 시각, Certbot 타이머 실행 이력, webroot 접근, 후크 종료 상태, 실제 제공 인증서 | 파일 갱신과 서비스 제공 인증서 갱신을 구분; 대기 프록시 먼저 검증. TLS 검증을 끄지 않음 |
| Nginx 502/504 | upstream 상태·앱 health·DB/Redis·요청시간·색상 확인 | 대기 실패 시 전환 금지, 전환 후 실패 시 기존 색상 복귀. timeout 수치만 늘려 숨기지 않음 |
| 메일 미수신/가입 실패 | SMTP 연결/TLS/인증 결과, 지정 수신함 도착, 증표 만료/재사용을 분리 | 인증 우회 금지. provider 접수 성공과 받은편지함 도착을 구분 |
| 구·신 색상 간 채팅 누락 | A는 blue 소켓, B는 green에 쓰기; 방송/DB/REST 복구 각각 관측 | 공유 DB만으로 SimpleBroker가 공유되지 않음. 재접속+DB 복구를 먼저 입증하고 공유 이벤트 전파 비교 |
| 동시에 같은 메시지 전송 | 같은 작성자/종목/requestId를 동시에 재전송, 다른 본문 충돌도 시험 | DB 1건 유지와 응답 계약을 모두 검사. 유일 제약 존재만으로 두 응답 모두 성공한다고 주장하지 않음 |
| 재접속 후 메시지 누락 | 조회 사이 30건 초과, 내 글 응답과 남의 글 경합, 중단된 트랜잭션의 지연 커밋 | 마지막으로 실제 읽은 커서와 반복 페이지 조회 점검. ID 할당 순서와 커밋 순서는 같다고 가정하지 않음 |
| Redis 장애 | 격리 환경에서 인증 저장소 장애와 캐시 장애를 분리 | 인증 코드/제한은 안전하게 거부하고 캐시 조회는 조건부 DB 우회. 모든 Redis 기능에 일괄 우회 금지 |
| DB 잠금/느린 조회 | 실제 MySQL에서 실행 계획·검사 행 수·잠금 대기·풀 대기 확인 | 원인별 인덱스/트랜잭션 범위 조정. 부하 조건이 다른 전후 결과 비교 금지 |
| 재기동/OOM/디스크 부족 | 양 색상 RSS·GC·OOMKilled·로그 증가·호스트 자원 확인 | 데이터 볼륨 유지, 검증된 이미지 재기동. JVM heap만 낮추고 메모리 원인 해결로 기록하지 않음 |
| DB 장애·백업 복원 | 격리 DB로 백업 복원 후 합성 회원 로그인·메시지 ID/내용/관심 목록 비교 | 컨테이너 재기동과 백업 복원을 구분. 마지막 복구 가능 시각(RPO)·복원 소요(RTO)를 실측 |

중요 회귀 실험: 트랜잭션 A가 낮은 ID를 할당받고 커밋을 지연하는 동안 B의 높은 ID가 먼저 조회되면 `id > afterId` 방식이 A를 놓칠 수 있다. 현재 발생 확인된 버그라고 단정하지 않으며, 실제 MySQL 동시성 시험으로 먼저 확인한다. 재현되면 겹쳐 읽기+ID 중복 제거, 방별 직렬화, 내구성 있는 이벤트 순서 등의 비용·한계를 비교한다. 단순 auto-increment를 커밋 순서 보증으로 쓰지 않는다.

## 6. 구조 개선 결정 순서

### A. Blue/Green과 데이터 보존

- 승인된 구·신 SHA를 고정하고 동일 MySQL·Redis를 사용한다. 파괴적 DDL 없이 새 컬럼/테이블 추가→양 버전 검증→전환→구버전 종료→후속 정리 순서를 검토한다.
- 대기 버전 health만으로 전환하지 않는다. 실제 API/인증 채팅 검사→전환→사후 검사→실패 복귀와 기존 데이터 확인이 필요하다.
- `deploy/bluegreen_smoke.py`는 Mailpit 격리 시험용이다. 실 SMTP 수신과 운영용 스모크가 준비됐다고 간주하지 않는다.
- 앱 롤백은 DB 롤백이 아니다. 구버전이 확장된 스키마에서도 동작해야 한다. 단일 EC2와 공유 DB는 호스트/DB 고가용성이 아니다.

### B. Redis 금융방 캐시 — 측정 후 적용

- 대상은 종목별 최근 30개, `afterId` 복구는 우선 DB. MySQL 커밋 뒤 캐시 무효화/갱신하고 TTL·용량을 제한한다.
- 캐시 채우기 중 새 글 저장과 무효화가 겹쳐 오래된 목록이 다시 저장되는 경합을 재현한다. TTL만으로 정합성이 해결됐다고 하지 않고 버전 확인·재시도·채우기 제어를 비교한다.
- 캐시 장애 시 DB 우회가 요청 폭증을 만들 수 있으므로 동시 요청/timeout 제한과 실패 응답도 시험한다.
- 기존 자료 p.5의 Redis 우선 쓰기 모델은 토스의 사례다. 현재 프로젝트에서 DB 원본을 바꾸려면 손실 범위·재처리·복원 근거를 먼저 제시해야 한다.

### C. Kafka와 공유 이벤트 — 금지하지 않되 채택 이유를 증명

| 후보 | 장점 | 검증해야 할 비용 |
|---|---|---|
| REST 폴링+DB 복구 | 현재 구조에서 복구 기준이 명확 | 조회 부하·표시 지연·커서 경합 |
| Redis Pub/Sub | 두 앱 간 빠른 방송 전파 후보 | 구독 중단 중 이벤트 보존 없음, DB 재조회 필수 |
| Redis Streams | 보존·ACK·재처리 후보 | 소비자 그룹은 분배이므로 각 앱 방송이 필요한 경우 별도 설계 |
| Kafka+outbox | 재처리·복수 후속 소비자·이벤트 이력 후보 | DB와 발행의 원자성, 파티션 내 순서, 그룹별 방송 설계, 운영 자원 |

Kafka 채택 시 DB 트랜잭션에 outbox를 기록하고 발행/소비의 중복을 전제로 식별키·재시도 한도·DLQ·재발행·lag·종료 처리를 검증한다. 하나의 consumer group은 모든 앱으로 방송하는 장치가 아니다. Kafka의 보장과 DB 쓰기·메일·브라우저 표시까지의 보장은 별개다. 4GB EC2에 브로커를 바로 얹지 않고 격리 환경의 CPU/RSS/디스크 측정부터 한다. 자료 p.4의 특정 offset 변경은 범용 처방이 아니며 재처리 범위와 중복 부작용을 먼저 검증한다.

## 7. 현재 첫 장애 기록 — IP 인증서 연결 실패

- 관찰: 2026-11-12 사용자 실행 결과에서 Certbot standalone 인증의 HTTP 접속 timeout 발생.
- 영향: 첫 공인 IP 인증서 발급 실패. 기존 운영 사용자의 장애가 발생했다고 주장하지 않는다.
- 확인된 사실: 이전 `ss` 출력에는 80 리스너가 없었다. 이는 외부 접속 허용 여부를 입증하지 않는다. CA가 요청한 주소의 TCP 연결을 완료하지 못했다는 오류가 있다.
- 가설: 현재 IP 불일치, 연결된 보안 그룹의 80 소스 제한, 호스트 방화벽, subnet route/ACL. **어느 하나도 아직 원인 확정 아님.**
- 다음 증거: 현재 EC2 공인 IP, 실제 연결된 보안 그룹의 HTTP 80 규칙, UFW 상태. 모두 정상이라면 경로/ACL과 제한된 연결 추적으로 이동.
- 완료 조건: 원인에 대한 변경 전후 증거, 첫 발급 성공, 이후 webroot 갱신 시험, 실제 외부 HTTPS의 인증서 확인. 현재 상태 OPEN.

## 8. 사례 기록 템플릿과 공개 범위

새 사례는 `docs/troubleshooting/YYYY-MM-DD-핵심증상.md`에 작성한다. 기존 비공개 progress/troubleshooting/scorecard 전체 업로드는 하지 않는다.

```markdown
# 핵심 증상과 원인 (날짜)
상태: 관찰 / 재현 / 원인 확인 / 수정 / 재검증
분류: 실제 운영 장애 / 격리 장애 실험 / 성능 실험
환경: 커밋, 이미지, 사양, 스키마 버전, 부하 조건 (비밀 제외)
사용자 영향: 확인된 범위와 지속 시간, 아직 모르는 범위
관찰·타임라인: 탐지→가설→조치→복구, KST와 request ID
가설과 반증: 무엇을 확인해서 어떤 후보를 제외했는가
원인: 로그/코드/재현 결과로 확인한 인과 관계
대안 비교: 최소 2개와 선택·미선택 이유
변경: 실제 파일/함수/PR, 구조가 어떻게 달라졌는가
시험: 입력·기대 결과·관찰 결과·반복 수·실행하지 못한 항목
측정: 동일 조건 전후 지연/오류/자원/정합성, 합성 데이터 표시
복구: 이전 버전/백업으로 되돌릴 조건과 보존 확인
남은 위험·재발 방지: 회귀 시험·알림·런북·담당 작업
객관적 평가: 개선 증거 충분 여부, 다른 원인 가능성, 채택/보류
```

원본 로그·DB 덤프·프로파일·메트릭 원본은 접근 제한된 위치에 보관하고 문서에는 비밀 제거된 최소 근거만 싣는다. 금융 원본 가격, 비공개 MAE/CI, 실제 회원/대화 본문은 공개하지 않는다. “성능 35% 개선” 같은 기존 프로젝트 수치를 이 프로젝트에 옮기지 않는다. 실제 장애를 만들기 위해 운영을 중단하지 않는다.

## 9. 포트폴리오로 남길 최대 3개 심화 사례

1. **배포와 복구:** IP HTTPS 장애 원인 추적, 인증서 갱신, 두 버전의 공유 DB, 전환 실패 시 복귀. 증거가 모인 범위까지만 완성 사례로 작성.
2. **채팅 정합성:** 중복 요청·색상별 연결·재접속·커서 경합. ID 기반 재현과 실제 MySQL 회귀 시험으로 설계 선택을 설명.
3. **측정에 따른 구조 변화:** 조회 병목→인덱스/캐시, 또는 이벤트 전달 요구→메시지큐. 개선이 없으면 도입하지 않은 판단도 기술적 결과로 포함.

각 사례는 요구사항, 변경 전 구조, 원인 증거, 대안, 변경 후 구조, 측정 결과, 비용과 한계 순서로 작성한다. 코드 구현·실제 운영·연구 성과를 분리하여 설명한다.
