# 이메일 인증 남용 방어와 웹 연결 계약

2026-10-29 최신 일일 계획의 남은 회원 흐름을 구현했다. 분기점 외에는 작업을 이어가라는 사용자 요청에 따라 SMTP 실수신과 운영 배포만 외부 입력으로 분리했다.

## 구현

- 이메일별 발송 60초당 1회, 1시간당 5회. 제한 식별자는 공백 제거·소문자화하되 실제 회원 이메일은 기존 정확 일치 정책을 유지한다. 기존 데이터의 대소문자 정규화 이관은 별도 점검 대상이다.
- IP별 10분 기준 발송/가입 10회, 코드 확인 60회, 로그인 30회. 임의 X-Forwarded-For를 신뢰하지 않고 remoteAddr를 사용한다. 프록시 뒤에서는 신뢰할 프록시와 실제 IP 전달을 운영에서 검증해야 하며, 미설정 시 프록시 한 IP로 합산돼 과도하게 제한될 수 있다.
- 각 코드의 오입력은 5회까지만 허용하며 마지막 실패 때 코드를 폐기한다. 새 발송은 이전 가입 증표도 무효화한다. Redis Lua가 횟수와 소진을 처리한다.
- 429 응답은 Retry-After를 포함한다. SMTP 오류는 해당 코드만 조건부 폐기한 뒤 503, Redis/DB 접근 오류는 503으로 실패한다. 실패 요청도 발송 제한에 포함해 반복 실패를 통한 남용을 막는다.
- SMTP 연결·읽기·쓰기 timeout 5초와 STARTTLS 필수, 명시적 발신 주소를 설정한다. 실제 비밀값은 추가하지 않았다.
- CORS는 설정된 정확한 Origin에만 POST/OPTIONS를 허용하고 쿠키를 사용하지 않는다. 기본은 로컬 개발 주소다. 운영에는 `app.auth.allowed-origins` 또는 `APP_AUTH_ALLOWED_ORIGINS`를 설정해야 한다.

이 수치는 프로젝트의 초기 정책이며 업계의 보편적 표준이라고 주장하지 않는다. 실제 이용량과 오탐을 확인해 조정한다. 분산 공격 전체를 해결하거나 CAPTCHA를 구현한 것은 아니다.

## 검증 기준

실제 Redis에서 오입력 폐기·재발송 초기화·오래된 SMTP 실패의 새 코드 보존·원자적 제한·식별자 격리를 검사한다. MockMvc의 발송→확인→가입→재사용 거부→로그인 흐름은 Redis와 비밀번호 인코더를 실제로 사용하되 회원 DB·SMTP·토큰 발급기는 대역이다. 프록시 헤더 위조와 429/503 오류 계약을 단위 시험한다. 전체 Java 시험·실행 JAR 검사는 원격 CI에서 실행하고 PR에 결과를 기록한다. 로컬 Gradle/JDK 제약은 이전 리뷰와 동일하다.

## 남은 분기

실제 SMTP 발신 설정·시험 수신처, 운영 Java URL·DB·Redis·CORS·프록시 설정이 필요하다. 실메일을 보내지 않았으며 공개 가입을 활성화하지 않았다. 웹은 별도 저장소의 `/signup`, `/login`에서 같은 API 계약을 호출한다. 운영 입력 없이 실제 수신이나 두 서비스 배포 완료를 주장하지 않는다. 금융 채팅은 다음 사용자 흐름이다.
