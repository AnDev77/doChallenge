# EC2에서 웹과 Java 연결 확인

- **시작 (2026-11-13 KST):** Java 원격 main `553d113`을 기준으로 작업했다. 사용자는 SSM 읽기 전용 연결 성공을 보고했다. 실행 환경에서 EC2 공인 HTTPS는 시간 초과됐으며 서버 중단을 단정하지 않는다. Blue/Green은 #13 이후 초안 계열이며 main에는 단일 스택만 있다.
- **중간:** Nginx의 `/healthz`가 응답하더라도 Java에 연결된 것은 아니다. 공개 HTTPS에서 QQQ와 SPY의 JSON 읽기, 정확한 Vercel Origin, 회원가입 및 채팅 작성의 브라우저 OPTIONS 요청을 각각 검사한다. 본문이나 서버 오류의 상세 내용은 출력하지 않는다. POST와 회원 자격 증명은 사용하지 않는다.
- **작업량과 시험:** 실행 스크립트, 합성 서버 시험, 기존 CI 연결, SSM 설정 문서 수정, 이 리뷰를 추가했다. 로컬 Python 전체 10개에서 정상 경로, Nginx만 성공하는 상황, HTML 200, 잘못된 종목, 허용되지 않은 Origin/헤더, TLS 실패와 리다이렉트 거부를 확인했다. 로컬 Java 빌드/실행 JAR은 Gradle 다운로드 제약 시 원격 게이트로 확인한다.
- **운영 증거와 한계:** 아래 검사는 프록시와 Java 읽기·브라우저 접근 경로만 판정한다. 실제 SMTP 수신, 회원 가입·로그인, 두 브라우저 채팅, 스키마 호환과 기존 데이터 보존, Blue/Green 전환·되돌리기는 별도다. 기동하지 않았고 Vercel 공개 플래그를 변경하지 않았다.

```bash
python3 -B deploy/verify_web_api.py --api https://<공인-IP-또는-도메인>
```

외부 HTTPS를 확인할 수 있는 단말에서 실제 주소로 실행한다. 모두 통과하면 보호된 미리보기에서 지정된 수신함으로만 메일을 시험한다. 이후 신규 계정 가입·로그인, QQQ/SPY의 두 브라우저 작성·조회·재접속을 확인한다. 공개 베타는 이 통합 검증과 전환 복구 확인, 채팅 운영 보호가 충족된 뒤에 판단한다.
