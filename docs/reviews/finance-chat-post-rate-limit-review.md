# QQQ·SPY 채팅 글쓰기 제한 검토

## 시작

2026-11-13 기준 원격 `main`은 `553d113`이고, #10~#21의 배포·스키마·관심 목록 작업은 별도 초안으로 열려 있다. `main`의 `FinanceChatService.post`는 요청 ID 재시도 중복을 방지하지만 인증 회원의 연속 글쓰기에는 제한이 없었다. 공개 채팅의 남용 방어는 제품 출시 조건이므로, Java 회원·채팅 범위 안에서 이 한 기능을 선택했다. 기존 미커밋 작업 트리는 건드리지 않았다.

## 중간

새 `FinancePostLimiter` 계약과 Redis 원자 카운터를 추가했다. 회원 한 명에게 QQQ·SPY 두 방을 합쳐 60초에 새 글 10건을 허용하며, Blue/Green 두 앱이 동일 Redis를 사용하면 같은 한도를 공유한다. 이미 저장된 동일 요청 ID의 동일 본문 재시도는 한도를 소비하지 않고 기존 응답을 반환한다. 다른 본문으로 같은 ID를 쓰면 기존 충돌 처리를 유지한다. 초과 시 채팅 전용 오류와 `Retry-After`를 반환하며, Redis 조회 결과가 없으면 쓰기를 차단한다.

로컬 Gradle 배포 파일을 가져오는 과정에서 네트워크가 차단돼 Java 전체 시험과 JAR은 로컬에서 실행하지 못했다. 이 실패를 시험 통과로 기록하지 않고, PR의 실제 Redis 통합 시험과 전체 Java/JAR 원격 게이트로 확인한다.

## 완료 판정과 한계

변경 범위는 Java 코드 5개, 시험 2개, 원격 게이트 1개, 이 리뷰 1개다. 서비스 시험은 신규 글의 저장 전 제한과 동일 요청 재시도의 한도 비소비를 검사한다. Redis 통합 시험은 서로 다른 두 제한기 인스턴스가 회원 한도를 공유하는지, 다른 회원은 독립적인지, 429와 재시도 시간을 반환하는지 검사한다. `chat-quality.yml`은 실제 Redis 시험이 생략되지 않았는지와 실행 JAR의 구현 클래스 포함을 확인한다.

이 제한은 고정 60초 창으로, 분산 배포 중 별도 Redis를 쓰면 한도를 공유하지 못한다. DB 저장이 실패한 신규 시도도 한도를 하나 소비한다. 제한만으로 신고·삭제·운영자 대응, 실제 EC2 이메일 수신과 두 브라우저 채팅, 운영 Blue/Green 전환을 검증한 것은 아니다. Python의 미래 정답과 예측 성능·제품 수요도 계속 HOLD다. 초안 PR은 병합·배포하지 않는다.
